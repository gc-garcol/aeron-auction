Architecture · Aeron Auction

Writes go through the log. Reads go straight to the leader.

The two sides at a glance

Both sides start at the same REST API and share one agent thread, one correlation ID sequence and one timeout. They split when the agent sends the request.

Write side Read side
Requests POST /auctions, POST /auctions/{id}/bids GET /auctions/{id}, GET /auctions
Transport Aeron Cluster ingress and egress, through an AeronCluster session Plain Aeron UDP publications and subscriptions: stream 1101 for requests, 1102 for replies
Added to the log Yes, and recorded to disk by Aeron Archive No, unless the read falls back to the log
Runs on All 3 nodes, in the same order The leader answers. Followers consume the request and ignore it
Entry point on the node AuctionService.onSessionMessage AuctionService.doBackgroundWork, which calls ReadChannel.poll
Time source The timestamp of the log entry cluster.time(), the time of the last log event
Consistency Committed by a majority before it's applied Committed state, which can be briefly stale after a leader change
Back-pressure The agent fails the request with 503. The service retries a reply up to 1,000 times, then drops it The leader offers a reply once. If that fails, it drops the reply and the client times out

Write side

Only log callbacks change state, and they take time only from the log. That's why every node reaches the same winner, and why an auction closes correctly after the leader dies.

Step What happens Library and API
HTTP AuctionController builds a Request and passes it to ClusterGateway, which calls ClusterRpcAgent.submit. That queues the request and returns a future. The HTTP thread never touches Aeron. If the queue of 4,096 is full, the caller gets 503. Spring MVC with CompletableFuture; Agrona ManyToOneConcurrentArrayQueue
W1 The agent thread takes up to 64 requests per cycle, assigns a correlation ID, encodes the command and offers it to the leader on :9002. It then starts a timeout (RPC_TIMEOUT_MS, 2 seconds by default). A failed offer returns 503. Aeron Cluster AeronCluster.offer; SBE codecs; Agrona AgentRunner, BackoffIdleStrategy, DeadlineTimerWheel, Long2ObjectHashMap
W2 The leader's consensus module gives the command its place and timestamp in the log, and sends it to the followers. Each node records the log to disk. The entry commits once a majority, 2 of 3 nodes, has it. Aeron Cluster ConsensusModule; Aeron Archive; Aeron Transport (aeron:udp?term-length=16m)
W3 Each node's AuctionService receives the committed command, decodes it and calls AuctionBook.create or placeBid with the log timestamp. A malformed message is ignored. A new auction also joins AuctionTimers. Aeron Cluster ClusteredService, ClusteredServiceContainer; SBE codecs
W4 The service sends the reply through the session, and only the leader's reply goes out. On the client, pollEgress delivers it to onReply, which matches the correlation ID, cancels the timeout and completes the future. ClusterGateway then maps the status to an HTTP response, and publishes a successful write as a live update (see Live updates). Aeron Cluster ClientSession.offer, EgressListener; SBE codecs

Closing an auction. One replicated timer ticks every 128 ms while any auction is open. Each tick advances an Agrona timer wheel using log time and closes expired auctions in ID order, so all nodes agree. The timer wheel isn't saved in a snapshot. It's rebuilt from the open auctions when a snapshot loads.

Recovery. onTakeSnapshot writes the next auction ID, the last timestamp and every auction, and a restarting node loads that snapshot. Followers treat the leader as lost after 3 seconds without a heartbeat. The client keeps its session alive every second and tries to reconnect every 500 ms.

Read side

Reads used to add an entry to the log for every request, which also meant writing to disk on all 3 nodes. Now they go directly to the leader. They run on the service thread, so they can read AuctionBook without locks, and that's also why this code must never block, retry or change state.

Step What happens Library and API
Setup ClusterReadChannel sends ReadHeartbeat with its reply address (:9007) to the node that the session reports as leader. It repeats every 250 ms until acknowledged, then every second, and at once when the leader changes. ReadChannel opens a reply publication, and only the leader answers with ReadReady. A node accepts up to 32 clients and drops one after 10 seconds without a heartbeat. Aeron Transport asyncAddExclusivePublication, ChannelUri; Agrona Int2ObjectHashMap
R1 The agent encodes a read as usual and offers it to the leader's :9006, but only if that leader acknowledged within the last 3 seconds. It uses the same pending map and timeout as a write. Otherwise the read goes through the log (see Fallback below). Aeron Transport ExclusivePublication.offer, with a 1 MB sparse term; SBE codecs
R2 ReadChannel.poll handles up to 16 fragments per call and runs AuctionBook.get or list. An auction past its deadline reads as closed, even before the tick has processed it. Write commands and malformed messages are counted and ignored. The class has its own codec and buffer, because Aeron can call it partway through a service callback. Aeron Cluster ClusteredService.doBackgroundWork; Aeron Transport Subscription.poll; Agrona ExpandableArrayBuffer
R3 The leader offers the reply once. On the client, a fragment assembler rebuilds it, because a large page can span several fragments, and the same onReply used by writes completes the future. Aeron Transport FragmentAssembler, Subscription; SBE codecs

Fallback. A read goes through the log if the read channel isn't ready or its offer fails, such as during a failover, and it's then handled in onSessionMessage. Setting READS_THROUGH_LOG=true sends every read that way. The auction.rpc.reads metric counts each route with its route tag.

Live updates

The web UI used to learn about other people's bids only by polling every 2 seconds. Now Centrifugo pushes each committed write to every open page over WebSocket, and polling slows to every 15 seconds as a safety net. Frames are binary: the browser speaks Centrifugo's protobuf protocol, and the event inside is protobuf too.

Step What happens Library and API
Setup The page asks GET /realtime where to connect, and gets Centrifugo's WebSocket URL and the channel auctions, or 204 if live updates are off. It connects without a token, because the feed is public and browsers may only subscribe. For the same reason Centrifugo accepts any origin; centrifugo.allowedOrigins narrows it. centrifuge-js protobuf build, subprotocol centrifuge-protobuf, on Centrifugo's public port :8000
L1 When the cluster replies OK to a create or a bid, ClusterGateway encodes an AuctionEvent with the auction's new state and posts it to Centrifugo's server API with X-API-Key, on the internal port :9000 of centrifugo-internal in namespace centrifugo. This runs after the reply and never waits, so a slow or missing Centrifugo can't delay or fail a request. Each client pod publishes the writes it handled, so an event goes out once. protobuf-java, generated from auction_event.proto; java.net.http.HttpClient.sendAsync; POST /api/publish with b64data, set by CENTRIFUGO_API_URL
L2 Centrifugo pushes the event to every subscriber as a binary frame. The page decodes it with auction-event.js and updates that auction in place. A bid is kept only if it's higher than what the page shows, because two client pods can publish out of order. A new auction refreshes the list, since its place depends on the page, filter and order. Centrifugo channel history (100 events, 5 minutes); protobuf wire format

Closing. The cluster closes auctions on its own timer, which no client sees, so there is no close event. Instead the page refreshes once an auction it shows passes its deadline.

What it doesn't promise. Live updates are best effort. A publish that fails is counted in auction.realtime.publish{result="failed"} and logged once, and the page catches up at its next poll. A page that reconnects within 5 minutes gets missed events from history; after longer, it refreshes. History is in Centrifugo's memory, so it runs as one replica, and more would need Redis or NATS. The REST API stays the source of truth.

Deployment

On Kubernetes, the auction runs in one namespace and Centrifugo in another, installed with the official Centrifugo chart. They share only the server API key, held in a Secret in each namespace. The aeron-auction chart can also run Centrifugo itself, in the same namespace, which is simpler for a local cluster. Docker Compose runs it as one more service.

Namespace Runs Installed with Reached by
auction StatefulSet of 3 cluster members, Deployment of 2 clients The aeron-auction chart with values-centrifugo-external.yaml Browsers on :8080. Members and clients reach each other over UDP
centrifugo Deployment of 1 Centrifugo, with history in memory centrifugal/centrifugo 13.7.1 with infra/k8s/centrifugo/values.yaml Browsers on centrifugo:8000 (WebSocket only). Client pods on centrifugo-internal:9000 (server API), across namespaces

Keeping Centrifugo apart lets it be upgraded, scaled and shared without touching the auction release. More than one replica needs Redis or NATS as its broker, because history is in memory. Only the WebSocket port is published, so publishing stays inside the cluster.

What a caller sees on failure

Status Cause Did the command apply?
400 404 409 The state machine rejected it: invalid input, unknown auction, auction closed, bid too low, or the seller bidding It was processed, and it changed nothing
503 Queue full, back-pressure, or no session No, it was never sent
503 The session was lost while waiting for a reply Unknown. A write may have applied, so check with GET before retrying
504 No reply within the timeout, including a reply the read channel dropped Unknown for a write, so check with GET. A read changes nothing and is safe to repeat
